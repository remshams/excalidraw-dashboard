excalidraw-dashboard architecture

excalidraw-dashboard is a self-hosted Excalidraw for one user, with a list of named drawings. A React client embeds @excalidraw/excalidraw and autosaves each drawing to a small Hono server, which stores it in SQLite through node:sqlite. Node 24 runs the server's TypeScript directly; only the client has a build step. Each drawing can have a preview image, whose URL carries a version (ADR 0001), and any number of tags. Numbered migrations keep the database schema up to date (ADR 0002).

Domain language

  • Drawing: an entity with an ID, a name, timestamps, a scene and a set of tag IDs. It is the aggregate root: its name, scene, preview and tags change only through the drawing. Assigning tags isn't an edit, so it leaves updatedAt alone.
  • Scene: a value object, the Excalidraw scene serialized with serializeAsJSON(..., "local"). It matches an exported .excalidraw file. A new drawing has no scene yet.
  • Preview: a PNG image of a drawing's scene. It is a value object that belongs to the drawing; setting a new one replaces it. previewUpdatedAt records when it was last set.
  • Drawing summary: a drawing without its scene or preview image, as a card on the landing page shows it. It carries the drawing's tag IDs.
  • Tag: an entity with an ID, a label and a colour, and the root of its own aggregate. Tags belong to the dashboard, not to one drawing; a drawing refers to them by ID. A label is trimmed, 1 to 30 characters long and unique when case is ignored. The colour is one of 8 open-color hues. Tags are dashboard data: they live in the database and never in a scene, so an exported .excalidraw file carries none.

Context

Excalidraw's code is bundled into the client, so it isn't an external system. Its canvas fonts are not: no asset path is set, so Excalidraw loads them from esm.sh when the canvas shows text.

The database holds every drawing and tag. A file copy of DATA_DIR is a consistent backup only while the server is stopped; a live backup uses SQLite's VACUUM INTO. The browser stores nothing; the URL names the open drawing.

Processes

In development, pnpm dev starts the server with node --watch and the Vite dev server for the client, which proxies /api to the server. In production, the server also serves the Vite build from ./dist and answers every other path outside /api/ with index.html, so the client handles its own URLs, such as /drawings/<id>. An unknown path under /api/ gets a 404. The Dockerfile packages this production server: it builds the client in one stage and runs src/server/index.ts on Node 24 as the node user, with the database in /data.

Modules and dependencies

The Fallow zones in .fallowrc.json enforce these rules, and pnpm fallow:architecture fails on a forbidden import. e2e may import nothing from src/.

database opens the SQLite file and brings its schema up to date. Each migration runs once, in its own transaction, and PRAGMA user_version records the last one (ADR 0002). drawing-store and tag-store are the repositories; apart from the migrations, no other module contains SQL. index opens one database and hands it to both.

A drawing row holds the name, the timestamps, the scene as JSON text and the preview as a BLOB. Only the preview route reads the BLOB. The drawing_tags table holds which drawings carry which tags. It belongs to the drawing aggregate, so drawing-store writes it, and the summary queries read the tag IDs from it. Its foreign keys delete a drawing's rows when the drawing or the tag goes. tag-store owns the tags table, whose label_key column holds the label in lower case under a UNIQUE constraint.

Each aggregate has one route module. drawing-routes serves the drawing, its preview and its set of tag IDs, and checks the tag IDs and the preview's type and size. tag-routes serves the tags and checks their bodies against the rules in src/shared/tags.ts, which the client will check too. app mounts both under /api, answers any other API path with 404 and serves the client build. index is the composition root and holds no logic worth testing. Nothing enforces the dependencies inside the server beyond code review.

src/client/main.tsx is the composition root: it renders App and loads styles.css. src/client/drawings/ is the drawings feature, one bounded context around the Drawing aggregate. It has two modules: catalog/ lists, creates, renames, deletes and switches drawings and lists tags, and editor/ edits the open one and keeps its scene and preview saved. They don't import each other; both use api.ts at the root. search.ts, a domain service that finds drawings by a part of their name, sits at the root too. So does use-open-drawing-id.ts, and App uses it to track the open drawing: /drawings/<id> opens a drawing, and / opens none. App shows the landing page at / and the editor view otherwise: the editor below a bar with an "All drawings" link and the drawing's name. Cards and "All drawings" are DrawingLinks: real links to a drawing's path, so a middle click opens a new tab, while a plain click opens the drawing without loading the page. Any client module may import shared; the diagrams show only api, the main user. Nothing enforces the dependencies inside the client beyond code review.

App loads the open drawing with use-drawing and renders Editor with it. Editor only renders Excalidraw; the two hooks hold its behavior. use-preview gets the saved scene from use-autosave through settle, which Editor passes in, so it doesn't import use-autosave beyond a type. A preview is out of date when the drawing has none or when it's older than the last scene save, and only then is it rendered: a light PNG, at most 640 px on the longer side, from Excalidraw's exportToBlob. A scene with nothing visible removes the preview. A failed preview is only logged, and the next open tries again.

list/ holds the landing page, switcher/ the quick switcher and tags/ the tags. Directly in catalog/ stay PreviewImage, which the landing page and the quick switcher use, icons, which all of them use, use-modal-dialog, which the quick switcher and the tray use, use-drawings for App, and NameField and DeleteConfirmation. Only DrawingList uses those two today, but neither depends on it.

App renders DrawingList with the list from use-drawings and the tags from use-tags. A search field next to the heading filters the cards through search.ts, and a status says when no drawing has the name. The first card is a blank sheet that asks for a name and opens the new drawing. Every other card shows the drawing's preview on a sheet, with an <img> whose URL from api.ts carries previewUpdatedAt as a version. A drawing without a preview, or one whose preview fails to load, shows a blank sheet. Leaving a drawing sends its new preview's summary to use-drawings, so the card changes its URL and the browser loads the new image. A card renames its drawing through NameField and deletes it only after DeleteConfirmation. use-drawings remembers which drawings it deleted, so App can ignore a last save that was still in flight and fails once the drawing is gone. App takes the icons for its bar from icons.

tags/ holds the tag aggregate's part of the catalog. use-tags loads the tags once when App mounts and sorts them with localeCompare, as use-drawings sorts names, so a label such as "Ärger" sits with the A's and not after "Work". The Tags button next to the search opens TagTray, a native modal <dialog> below the button with a transparent backdrop, so the page stays in view but can't scroll (ADR 0003). The tray lists each tag with its colour and the number of drawings that carry it, which it counts from the drawing summaries. Its field finds tags through find-tags, a domain service: labels that start with the text first, then the rest. A status says when no tag has the text, when there are no tags yet or when they aren't loaded. Escape clears the find text, then closes the tray; a press beside the tray also closes it, and the focus returns to the button.

The editor view's bar has a "Switch drawing" button, and use-switcher-shortcut makes Ctrl+K or ⌘K toggle the same QuickSwitcher while the editor view is mounted. The hook listens in the capture phase and stops the event, so Excalidraw doesn't add a link on those keys. The switcher belongs to the catalog even though it shows over the editor, because it finds and creates drawings. It is a native modal <dialog>: the browser shows it above Excalidraw's layers, makes the page behind it inert and returns the focus when it closes. It stops key events at the dialog, and it sits outside Excalidraw's container, so they don't reach Excalidraw's shortcuts. It lists the matches from search.ts by updatedAt, newest first, and last offers to create the query as a new drawing unless a drawing has that name. Choosing a row calls App, which opens or creates the drawing as the landing page does. The editor remounts on key={drawing.id}, so its pending save is flushed as when leaving through "All drawings".

styles.css holds what the whole client shares: design tokens for colors from open-color, the palette Excalidraw draws with, and for font sizes, line heights, font weights, stroke widths, corner radii and spacing, with a --tag-<colour>-solid for each of the 8 tag colours in both palettes; Excalidraw's bundled fonts, Excalifont for drawing names and Assistant for controls; the base rules; and the focus ring. It switches to a dark palette with prefers-color-scheme. Each component keeps its own rules in a CSS module next to it, such as DrawingList.module.css, so its class names can't clash with another component's. PreviewImage's module gives previews, which are stored light, Excalidraw's own canvas filter in dark mode. use-color-scheme reads the same setting for App, which passes it to Editor. Editor hands it to Excalidraw and hides Excalidraw's own theme toggle. The theme is display state only: Excalidraw leaves it out of the stored scene, so a theme change saves nothing.

Runtime flow

App, DrawingList and hooks folds App, DrawingList, use-drawing and use-drawings into one lane. save-scheduler imports nothing; use-autosave gives it the function that saves. Going back to all drawings or leaving the page flushes a pending save, and reopening the drawing loads its scene again. Saves run one at a time: the server keeps whichever write lands last, so a newer scene waits for the save in flight.

The same check runs when a drawing opens, which gives drawings saved before previews existed a preview and repairs one a closed tab left out of date. The browser seldom finishes an export during pagehide, so that path is best effort. Both lanes call the server through api, which this diagram leaves out.

HTTP API

RouteMethodPurpose
/api/drawingsGETList drawing summaries, sorted by name
/api/drawingsPOSTCreate a drawing; a blank name becomes Untitled
/api/drawings/:idGETGet a drawing with its scene
/api/drawings/:idPUTChange the name, the scene or both
/api/drawings/:idDELETEDelete a drawing
/api/drawings/:id/previewGETThe PNG preview, cached as immutable
/api/drawings/:id/previewPUTStore an image/png body of at most 2 MB
/api/drawings/:id/previewDELETERemove the preview
/api/drawings/:id/tagsPUTReplace the drawing's tags with { tagIds }
/api/tagsGETList tags, sorted by label with case ignored
/api/tagsPOSTCreate a tag from { label, color }
/api/tags/:idPUTChange a tag's label and colour; both required
/api/tags/:idDELETEDelete a tag and remove it from every drawing

Unknown drawings, and a drawing without a preview, answer 404. Preview uploads answer 415 for another content type and 413 above 2 MB. The PUT and DELETE on a preview return the drawing summary; they change previewUpdatedAt, not updatedAt. Clients are to add ?v=<previewUpdatedAt> to the preview URL (ADR 0001). Scenes have no body limit, because scenes with embedded images can be large.

An unknown tag in the path answers 404. A tag body that isn't JSON, lacks a label, breaks the label rules or names an unknown colour answers 400. So does an assignment body that isn't JSON or lacks an array of tag IDs, and an assignment with an unknown tag ID, which then changes nothing. A label another tag has, ignoring case, answers 409. Errors are plain text. PUT /api/drawings/:id/tags returns the drawing summary and leaves updatedAt alone; a tag ID sent twice counts once. Summaries list tag IDs sorted by ID; clients sort them for display. src/shared/drawings.ts and src/shared/tags.ts hold the request and response types.

Tests and quality gates

Vitest runs three projects from vite.config.ts:

  • server tests the API through app.request against an in-memory SQLite database, including the cascades when a tag or a drawing is deleted. Each route module has its own test file, and app.test.ts covers the API 404 and the client build. test-api.ts gives each test a fresh database and holds the request helpers. database.test.ts opens database files from before numbered migrations, with and without previews, in a temporary folder, to test the upgrade.
  • shared tests the tag label and colour rules.
  • client tests in jsdom with Testing Library. Component tests mock api.ts and replace Editor.tsx, since Excalidraw does not render in jsdom. The editor hooks and preview.ts are tested with api.ts and Excalidraw's exportToBlob mocked.

pnpm check runs the typecheck, Biome lint and formatting, a Stylelint check that CSS modules use the design tokens, Vitest, the production build and the Fallow gates: dead code, duplicates, zone boundaries and health with a CRAP limit of 12. For health, pnpm coverage first writes coverage/coverage-final.json, which Fallow reads for the CRAP scores.

pnpm mutation runs mutation testing on changed code against origin/main and fails below the minimum score set in the mutation script. CI runs it on pull requests.

Playwright runs the end-to-end tests in e2e/ against the real application: the production build, the server, SQLite and Excalidraw in Chromium.

  • playwright.config.ts builds the client and starts the server on port 3101 with DATA_DIR=.e2e-data. The folder is deleted before each run and kept afterwards for debugging. The tests share this server and run one at a time.
  • drawings.spec.ts covers creating, renaming and deleting a drawing, opening one from its card or its URL, retracing drawings and the landing page with the browser's back button, a drawing surviving a reload, storing a preview when the user leaves a drawing or opens one that has none and showing it on the card, reopening a drawing right after leaving it, following the system's dark mode, searching the drawings by name, and showing a failed save. The reload test reads the saved scene from the API, then selects all shapes in the editor to show the scene was loaded back. The failed-save test deletes the open drawing through the API, as another tab would, then dismisses the error message above the editor. The preview-on-open test copies a drawn scene into a drawing created through the API, so that drawing has no preview yet.
  • tags-api.spec.ts covers tags through the HTTP API: creating, renaming and deleting a tag, assigning tags to a drawing without changing its updatedAt, and that deleting a tag removes it from the drawing.
  • tags.spec.ts covers the Tags tray: the rows with their colour and drawing count, where the tray hangs on a wide and a phone-width window, fitting a short window that can't scroll, finding a tag, using it by keyboard alone with the focus returning to the button, and closing it with a press beside it. Tags and assignments come from the HTTP API.
  • app.spec.ts checks that the page names the Excalidraw logo as its icon and that the server serves it as an SVG.
  • Each test groups its actions and checks into test.step blocks, so the test and its report read as a scenario.
  • drawings-ui.ts holds the locators and user actions for the drawings UI, and drawings-api.ts creates and deletes drawings, stores scenes, assigns tags, and reads stored scenes, previews and summaries through the HTTP API. tags-api.ts creates, changes and deletes tags and reads them back, and tags-ui.ts holds the locators and user actions for the tray. None of them defines steps. unique-name.ts gives every drawing and tag a name no other test uses.

The tests are black-box. They run with pnpm e2e and in the e2e CI job, not in pnpm check.
